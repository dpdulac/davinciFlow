6. Apply `ShotFilterLine` logic (e.g. if the user only wants shot 0050 out of the 100-shot playlist).

## AgX Pipeline Configuration (.drx files)
Due to DaVinci Resolve Scripting API limitations, the script cannot programmatically generate Color Space Transform (CST) and DCTL nodes on the fly. To support the Camera AgX workflow, the script relies on pre-saved DaVinci PowerGrades (.drx files) placed in the `drx/` subdirectory.

When `AgxCheck` is enabled, the script dynamically applies one of three node trees depending on the media type:
1. `drx/AgX_mov_proxy.drx`: Applied to standard video proxies (.mov, .mp4, DNxHD, etc.)
2. `drx/AgX_img.drx`: Applied to standard image formats (.png, .jpg, .tga)
3. `drx/AgX_exr.drx`: Applied to .exr files.

**Standard Color Science Setup for DRX files:**
Assuming the Camera AgX DCTL expects an **ARRI LogC3 / Wide Gamut 3** working color space, configure your nodes as follows and export the still as a .drx file:

- **AgX_mov_proxy.drx (Rec.709 Proxies)**
  - Node 1: CST (Input: Rec.709/Gamma 2.4 | Output: ARRI Wide Gamut 3/ARRI LogC3)
  - Node 2: Camera AgX DCTL
- **AgX_img.drx (sRGB Images)**
  - Node 1: CST (Input: sRGB/sRGB | Output: ARRI Wide Gamut 3/ARRI LogC3)
  - Node 2: Camera AgX DCTL
- **AgX_exr.drx (EXR Sequences)**
  - Node 1: OCIO ColorSpace (Source: ACES - ACEScg | Target: Input - ARRI - V3 LogC (EI800) - Wide Gamut)
  - Node 2: Camera AgX DCTL

**IMPORTANT WARNING FOR CROSS-PLATFORM DEPLOYMENT (WINDOWS):**
Because the DaVinci Resolve `.drx` files encode node properties into a hexadecimal blob, absolute file paths (such as the path to your `config.ocio` file) are hardcoded into the blob and cannot be dynamically changed by this python script. 
If you install this script on a Windows machine, the OCIO path inside `AgX_exr.drx` (which points to a Linux `/s/prodanim/...` directory) will be invalid. You must open DaVinci Resolve on the Windows machine, manually update the OCIO node with the correct Windows path to your `config.ocio` file, and re-export the `AgX_exr.drx` file into the `drx/` folder to overwrite the Linux version.

## 7. NATIVE OCIO v2.5.1 & CTF PIPELINE GENERATOR (`export_tmnt2_ocio2_ctf.py`)
To upgrade legacy OCIO v1 show transforms (such as TMNT2) to modern high-speed pipelines without loss of mathematical precision, provide a standalone generator script: `export_tmnt2_ocio2_ctf.py`.
- **Environment & Optimization**: Run within `rez env ocio-2.5.1 pyocio-2.5.1`. The script loads the legacy 15-operation show profile and applies `processor.getOptimizedProcessor(ocio.OPTIMIZATION_LOSSLESS)` to collapse redundant matrices and range operations down to an optimized 8-9 operation chain.
- **Color Transform Format (.ctf) Support**: Why `.ctf` instead of Academy `.clf`? Standard `.clf` does not support `InverseLUT1D` nodes and forces lossy inversion baking. Autodesk/Academy Color Transform Format (`.ctf`) natively supports `InverseLUT1D`, matrices, and range operators, guaranteeing 100% mathematical equality to the original studio shaders without highlight clipping or interpolation drift.
- **Outputs Generated**:
  1. `tmnt2_native_look_v2.ctf`: Linear `ACEScg` to `SPI_anim` Rec.709 display look.
  2. `tmnt2_acescct_to_rec709_v2.ctf`: Logarithmic `ACEScct` to `SPI_anim` Rec.709 display look.
  3. `tmnt2_config_v2.ocio`: A lightweight, standalone OCIO v2.1 configuration file referencing the native CTF shaders for instant loading in DCCs and DaVinci Resolve.

### Loading `.ctf` and OCIO v2 in DaVinci Resolve
Because `.ctf` is an active OpenColorIO shader format containing complex mathematical formulas (like `InverseLUT1D`), DaVinci Resolve will **not** list it in the static right-click LUT menu (which only registers table formats like `.cube`, `.3dl`, or `.clf`).
To load the `.ctf` look in Resolve 21:
1. Go to the **Color Page** and open the **Effects (OpenFX)** panel.
2. Under **Resolve FX Color**, drag and drop **OCIO Display** (or **OCIO ColorSpace**) onto your color node.
3. In the Inspector / Settings panel:
   - Change **OCIO Config** from Default to **Custom File...** (or **FromFile**).
   - Browse and select the standalone config file: `/datas/dulacd/tmnt2_config_v2.ocio` (or `/s/prodanim/tmnt2/_sandbox/dulacd/tmnt2_config_v2.ocio`).
   - Set **Input Color Space**: `ACEScg` (for EXR) or `ACEScct` (for Log).
   - Set **Display Device**: `Rec.709-Screen`.
   - Set **View Transform**: `SPI_anim`.

### Dual-Workflow Architecture: Why `.cube` is Slower or Faster than OCIO Display
When testing timeline performance in DaVinci Resolve, you will notice that using an **OCIO Display** node is significantly slower than applying the baked **`.cube`** 3D LUT. This is intentional and comes down to hardware rendering architecture:
- **Why OCIO Display (.ctf) is Slower in Resolve**: OpenFX (OFX) plugins execute outside Resolve's ultra-fast core color node loop, adding API overhead per frame. More importantly, executing an OCIO v2 `.ctf` shader requires the GPU to actively compute an 8- to 9-step mathematical chain—performing matrix multiplications, power curves, and iterative floating-point approximations for `InverseLUT1D` tables—per pixel on every single frame.
- **Why `.cube` is Blazing Fast in Resolve**: When applying a `.cube` LUT directly on a node (or via a CST node), DaVinci Resolve loads the static 3D lookup table directly into GPU video memory as a 3D texture. Resolve's hardware shaders perform instantaneous tetrahedral interpolation with essentially zero computational overhead.

**Industry Standard Recommendation:**
- **For DaVinci Resolve (Real-Time Review & Editorial)**: Always use the **`CST (ACEScg ➔ ACEScct)` + `tmnt2_acescct_to_rec709.cube`** workflow (automatically applied by `davinciFlow` via `drx/tmnt2_0cio_exr.drx`). Converting scene-linear EXRs into log first preserves >1.0 highlight dynamic range without clipping while delivering smooth real-time 24fps/30fps playback.
- **For DCCs & Compositing (Nuke / Katana / Houdini / Arnold)**: Use the **`tmnt2_config_v2.ocio` and `.ctf` shaders**. Lighting and compositing software does not rely on real-time editorial playback; instead, they require 100% mathematically exact float32 calculations without table interpolation tolerances.
